# DFSC 社区插件市场：机制研究与上游反馈

> 作者视角：`dfsc-StepAudio`（StepAudio TTS MCP 插件）开发演练
> 初稿：2026-11-07；事实复核：2026-11-08
> 对象：AstrBot / DSH / Pi / DFSC。这里只比较公开机制，不做安全性排名。
> DFSC 宿主基线：`e419143435dcbc8e1519085a1c60e7054e24144d`；
> 社区市场基线：`99a4b871f18b02bfb4af83648cdc3e2bb384e114`。

## 一、先纠正初稿的四处判断

1. **不运行 npm/pip 不等于禁止依赖。** 作者可以使用 SDK 并在自己的构建环境打包；
   发布物须完整、可审查、可同步。`.gitignore` 含 `dist/` 不证明同步器按目录名禁用它。
2. **DFSC 已有显式更新。** 宿主主线已支持用户检查新版后更新同源插件并保留配置；
   市场 README 的卸载重装说明落后于宿主实现，不能据它判断更新器不存在。
3. **DSH 不再只能靠第三方市场插件。** 官方当前已有内置插件市场；
   `2BingLing/dsh-market` 是另一个社区方案，不能代替整个 DSH 的现状。
4. **固定提交和哈希不等于安全保证。** 移除“四家中最安全／最严格”的结论；
   它们证明来源与内容一致性，不证明没有漏洞、恶意行为或未来兼容问题。

以下“已有”指核对到的代码或文档，不代表本机安装包、每个账户或所有平台均已验收。

## 三、AstrBot 现行投稿与审核应如何理解

1. 按官方开发规范准备插件，包含元数据、使用说明、许可证和实际所需依赖；
   可以声明 AstrBot 版本范围等兼容信息。
2. 上传到 GitHub，在 `cloud.astrbot.app` 提交仓库 URL；文档写明审核通过后上架 [A1]。
3. 旧的 `AstrBot_Plugins_Collection` README 已将投稿指向 Cloud，不能继续指导作者去走旧入口 [A4]。
4. 官方另有 `astr-plugin-reviewer`：根据候选信息和源文件进行 AI 初审，生成分析报告；
   它自己的说明明确不能替代人工检查 [A3]。
5. **未知项保持未知：**本轮未核实当前 Cloud 是否对每个投稿强制使用该工具、
   人工复审如何分工、通过阈值、审核时限，以及每次后续更新是否重新完整审核。
   不把“有审核”写成“每次安装/更新均已安全认证”。

初稿中归于 AstrBot 的那句“无法完全保证……”未在本轮当前官方页面复核到同样措辞，
不再保留逐字引述。DFSC 需要风险声明，依据是我们自身的运行与信任边界，
而不是要求先证明竞品用了同一句话。

## 四、DFSC 仍需改进什么

- **依赖交付引导：**提供使用官方 MCP SDK 的真实 bundle 样例，验证跟踪、同步、
  固定提交、许可证和无 `node_modules` 安装。不把 BVR 的外部运行体要求普遍化。
- **公开契约：**已有展示、分类和设置规范应有单一作者入口；原生 MCP 启动子集、
  环境处理、未知字段及拟议 host 声明仍需版本化 schema 与有效/无效样例。
- **账户安全：**占位符不是授权协议。演练中的 Key 名不匹配说明不能靠作者 sentinel
  防止宿主默认注入；优先做默认隔离，再做有独立授权和撤销的通用 broker。
- **更新说明：**修订社区 README 的卸载重装旧文案，保留显式更新、来源绑定、
  配置保留、保守拒绝和重启生效的限制。旧安装包是否支持须单独核对。
- **投稿风险披露：**作者说明外部组件、文件/网络/进程行为、上传的数据、账户/额度影响、
  更新迁移和已测范围；市场审核这些声明，不以收录替代风险告知。
- **用户界面：**市场文档、投稿指南和安装/更新确认应使用一致边界；
  文档更新不代表客户端已有风险弹窗，不新增“安全认证”徽章。

### 设置 schema 变更与强制重装（2026-11-11 补充，dfsc-StepAudio 实测契约后提出）

> **状态：已落实（2026-11-13）**——宿主 PR #238「完善插件兼容更新与占用协助恢复」已合并：普通独立 json-file-v1 配置允许展示调整（label/help）、保留旧值的 enum 扩展、无 default 的非秘密可选新增，从活跃快照派生新 revision 并保留秘密/false/空串/服务开关；更新占用时展开二级界面说明受影响会话与恢复结果。仍不支持：default 增删改、必填性变化、类型变化（含 secret↔text）、复杂 host 绑定迁移。以下为原始诉求，保留备查。

现状（PLUGIN_AUTHORING.md）：首版保守拒绝“设置清单字节变化、MCP 服务名称、传输类型、默认开关、独立配置消费者标记变化”的更新，需要后续迁移流程。对插件作者这是一次性门：现在不加的字段，以后加了就要用户卸载重装、重填 Key。

诉求，按优先级：

1. **允许纯增量变更**：只新增可选字段、不动已有字段的类型和语义时，已安装实例应以 schema 默认值继续运行，不拒绝更新。真正危险的是删字段、改类型（尤其 secret→text）、改默认值语义——这些可以继续拒绝。
2. **拒绝时给出可操作提示**：更新被拒的用户现在看不到原因和下一步。至少在更新入口说明“该版本更改了插件设置结构，需卸载重装；已保存的 Key 不会自动迁移”。
3. **轻量迁移路径**：哪怕是“导出/导入配置”或引导重填 Key，也优于卸载重装。

配套事实（dfsc-StepAudio 已按现状设计，供讨论时参考）：我们的 8 个字段已按“一次想全”定稿；`model`/`mode` 等刻意用 text 而非 enum，就是为了把“新增选项”排除在字节变化之外——这是作者侧绕路，但根本解法在平台侧。

## 五、交付状态

- **已核实并已有：**固定提交同步、逐文件锁定、通用配置、显式同源更新。
- **文档需要对齐：**作者入口、SDK/依赖交付说明、更新说明、投稿风险披露。
- **仅规划：**通用账户 broker、默认凭据隔离、标准 host client、StepAudio 跟随接入 [F5]。
- **未来示例：**StepImage 复用通用层，但需要宿主新增并核验图像能力；
  不代表当前 Plan 已提供图像接口，不进入首版范围。
- **未在本轮执行：**真实账户/付费请求、插件代码迁移、市场条目更新、客户端打包或发版。
